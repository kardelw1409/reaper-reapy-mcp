## 0. Цель одной страницей

Понять до конца, как дать LLM-агенту возможность **искать, выбирать и (если безопасно)
сохранять пресеты НАТИВНОГО preset browser'а Vital** — через наш существующий MCP
(`C:\repos\reaper-reapy-mcp`), как **расширение его плагин-слоя (V3)**. Не через host-пресеты
REAPER (их Vital не отдаёт), не GUI-автоматизацией как основным путём, и **не отдельным
MCP-сервером** (это прямо запрещено в P26 Addendum 2 §1).

Почему задача существует: Vital импортирует/экспортирует пресеты внутри себя; REAPER-контролы
этого не видят. У нас уже есть провайдер/адаптер для накрутки звука по контролам (state
chunk-канал, транзакции, verify), но доступа к браузеру пресетов у него нет.

Целевые контракты (из P26 Addendum 2 §2 — это требования, а не обязательство их сразу делать):

| Контракт | Смысл |
|---|---|
| `preset_search` | поиск по запросу + доступные категории/теги; лимит результатов; пагинация при необходимости |
| `preset_apply` | применение выбранного результата по **устойчивому идентификатору**, с отображаемым именем для AI/пользователя |
| `preset_get_info` | метаданные выбранного пресета — только если доступны |
| `preset_save` | сохранение пресета — только если операция безопасна |
| `preset_init` | Init-состояние — только если известен надёжный способ |

Дисциплина из Addendum 2, которую нельзя терять: **Preset Catalog ≠ Capability Profile** —
индекс пресетов обновляется и версионируется независимо от описания контролов. И: «не обещай
полноценный поиск по категориям/тегам, если сам формат пресетов не содержит этих данных».

## 3. Вопросы исследования (на каждый — ответ с якорем)

### A. Источник правды внутреннего браузера
- A1: откуда браузер берёт factory-пресеты (встроены/файлы) и совпадает ли это с
  содержимым `Documents\Vital` на этой машине; если встроены — извлекаемы ли (ресурсы DLL) и
  что можно индексировать ЛОКАЛЬНО, не распространяя.
- A2: `Vital.library` / `Vital.favorites` — формат, роль, когда обновляются; увидит ли
  браузер новый файл в user-папке БЕЗ рестарта плагина (важно для UX «сохранить → показать»).
- A3: полный список того, что показывает браузер: папки/категории/теги/style/author — и что
  из этого ЕСТЬ в самом `.vital`, а что живёт только в индексе/UI (это границы `preset_search`).
- A4: семантика shadowing `User`-папки и как отличить factory/user-запись от одного пути.
- A5: роль `.vitalbank` (банки): индексируются ли браузером, нужны ли в поиске.

### B. Применение пресета (ядро исследования)
- B1: что именно делает загрузка пресета из браузера — из исходников, по списку каналов
  (settings/modulations/wavetables/lfos/sample/effect-order/macro names). Что НЕ заменяется.
- B2: **field-by-field таблица `.vital` ↔ document JSON** (документ = то, что лежит в track
  state chunk): что совпадает, что дефолтится, что отличается (synth_version, preset_name,
  отсутствующие ключи → дефолты, миграции). Эта таблица — главный технический результат.
- B3: можно ли собрать документ из `.vital` и записать его существующим codec-путём
  (наш `plugins/providers/vital/{codec.py,wavetables.py}`) — что уже есть, чего не хватает.
- B4: побочные эффекты, которые chunk-канал НЕ воспроизведёт (если есть): LFO-фазы,
  sample-rate-зависимое состояние, GUI-кэш, библиотечные указатели. Каждый — [И]/[К]/[П].
- B5: host-visible preset interface установленного Vital: точные живые ответы
  `TrackFX_GetPresetIndex` / `GetPreset` / `GetNamedConfigParm` / `EnumTrackMIDIProgramNamesEx`
  (ожидание: пусто/0 — но зафиксировать ФАКТ, не ожидание).
- B6: читается ли имя текущего внутреннего пресета с живого инстанса (есть ли `preset_name`
  в документе chunk) — от этого зависит `preset_get_info` на живом инстансе.
- B7: `Init`: что именно делает UI-пункт Init, есть ли надёжный файл/дефолт-документ для
  эквивалента.

### C. Сохранение
- C1: как плагин сериализует `.vital` (точка в коде): какие поля пишутся, что с `sample` и
  `wavetables`, byte-faithful ли writer; можем ли воспроизвести writer независимо.
- C2: что произойдёт при появлении нового файла в user-папке: обновится ли `Vital.library`,
  покажет ли браузер сразу (связать с A2).

### D. Архитектура расширения в нашем плагин-слое
- D1: где правильное место — методы провайдера Vital + форма tool-интерфейса: расширить
  `plugin_state` провайдер-хуком vs новые `preset_*` tools vs неймспейс capabilities.
  Аргументы и одна рекомендация. Напомнить себе: **не создавать отдельный MCP-сервер**;
  не смешивать Preset Catalog с Capability Profile.
- D2: индекс пресетов: где хранить (cache-каталог `%LOCALAPPDATA%\reaper_reapy_mcp\cache\...`),
  ключ инвалидизации (mtime+size+hash каталога/файлов), версионирование — независимо от
  профиля контролов.
- D3: `preset_search` семантика: поля запроса (имя/путь/author/style/подстрока), лимит,
  пагинация, **устойчивый идентификатор** (что брать: relpath+sha?); перф: замерить полный
  скан ~2226 файлов (секунды, сколько I/O).
- D4: безопасный workflow `preset_apply` на существующих примитивах: dry-run → запись →
  read-back verify → rollback при расхождении; что из этого есть в транзакционном слое.

### E. Риски
- E1: миграции версий; «preset newer than build rejected»; пресеты с `sample` (base64, размер)
  и `wavetables` (payload-лимиты — сверить с VERIFIED_PAYLOAD_BYTES из P30).
- E2: конкурентность: пользователь в этот момент сам грузит пресет; открытый GUI;
  что случится с нашей транзакцией.
- E3: GPL/trademark-рамки (см. §2): что можно/нельзя хранить и распространять.

## 5. Стадия B — эксперименты в песочнице (только по решению владельца)

Цель: доказать/опровергнуть ядро — «`.vital` из файла = документ = корректная запись через
существующий chunk-канал».

Правила песочницы (не смягчать): площадка — существующие треки `MCP_SMOKE_*` (или новый трек
с явным именем `MCP_SMOKE_*`) с инстансом Vital; пользовательские треки не трогать; перед
экспериментом — capture полного документа (digest), после — restore и **verify restore по
digest**, при несовпадении — СТОП и отчёт; проект НЕ сохранять; каждая запись с counters в
отчёте.

- **E-1 (основной)**: взять самый маленький реальный `.vital` (без `sample`), построить
  документ, применить через codec-путь, read-back: (a) выборка N контролов совпадает с файлом,
  (b) modulations/wavetables/lfos заменены как ожидается, (c) НЕТ необъяснённых расхождений;
  затем restore к исходному (digest-подтверждение).
- **E-2 (owner-assisted, опционально, ~1 минута руками)**: пользователь в GUI Vital один раз
  грузит заранее выбранный пресет; исследователь читает chunk и делает diff с документом,
  построенным из того же файла. Это единственный способ получить **[И] на «GUI-загрузка ≡
  наша запись»** — без этого заявлять эквивалентность можно только [К]. Согласовать с
  владельцем заранее; если отказано — так и записать в limitations.
- Если E-1 не проходит: зафиксировать точную точку отказа; GUI-автоматизацию упомянуть как
  задокументированный последний resort, не как план.

Короткий план (порядок чтения, список проб, оценка времени), затем исполнение. Вопросы
владельцу — только если без ответа нельзя двигаться (например, согласие на E-2).
