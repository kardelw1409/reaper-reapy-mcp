# 25. Работа с несколькими проектами (вкладками): адресация, параллельные агенты, блокировка

Дата: 2026-10-18. Автор: сессия P43. **Статус: ПЛАН — ничего не реализовано.**
Все числа ниже — из живых замеров этой сессии (read-only, REAPER 7, библиотека reapy, dist-API).

Решения владельца, дословно:

* «цель - работа в несколько проектов»;
* про рендер: «условно делать блокировку всего - переключать на то что надо рендерить - рендер -
  разблокировка и все, это можно было бы так сделать»;
* «делать где-то привязку на уровне процесса не ок, ведь может быть ситуация что придётся работать
  агентом одним в двух табах» → **привязка только на уровне вызова**, вариант «сервер-на-проект»
  (env-переменная на процесс) ОТВЕРГНУТ.

### 1.3 Уже существующий дефект: `project_id` манифеста пинует ПОЛОВИНУ

`apply_audiocpp_manifest(project_id=…)` (`src/reaper_reapy_mcp/manifest/apply.py`) пинует:

* `project = reapy.Project(project_id)` (стр. 716) и все чтения (`project.name`, `_track_names(project)`,
  `_enumerate_marks(project)`);
* `project.tracks[index].delete()` (стр. 796), `RPR.AddProjectMarker(project.id, …)` (стр. 805),
  `RPR.DeleteProjectMarker(project.id, …)` (стр. 787), `_set_time_signature(project, …)` (стр. 803).

НО записи «через контроллер» идут в **текущую** вкладку (стр. 798, 818, 834, 836, 843, 958, 1154):
`controller.set_tempo`, `controller.create_track`, `controller.insert_audio_item`,
`controller.insert_midi_item`, `controller.set_item_position`, `controller.get_track_count`,
`controller.get_tempo` — все они зовут `reapy.Project()` без проекта.

**Следствие:** если между `new_project_tab` и заливкой выделение сменилось — удаление AI_*-треков
произойдёт в пришпиленном проекте, а создание — в том, что на экране. Докстринг обещает «оба вызова
работают с одним проектом»: это верно, только пока текущая вкладка = пришпиленная.
Этот дефект стоит закрыть **независимо от всей затеи** (фаза 0 ниже).

## 2. Барьеры (что мешает сегодня)

1. **Адресация.** Все контроллеры и плагиновый слой берут «текущую» вкладку
   (`reapy.Project()` / `GetTrack(0, …)`). Переключение вкладки в REAPER глобально — оно меняет
   адресацию у ВСЕХ агентов сразу, включая человека за экраном.
2. **Идентичность цели.** В `location` нет проекта → токены, evidence, «какая это инстанция»
   смешивают вкладки с одинаковыми индексами треков.
3. **Глобальные действия.** Рендер и открытие вкладки привязаны к текущей вкладке по природе
   REAPER (`Main_OnCommand`); пинуется только `Main_OnCommandEx` — если замер подтвердит (п. 6.1).
4. **Между процессами.** Локи у нас per-process, reapy их не имеет вовсе. Чужую правку поймает
   verify-on-write (отказ вместо порчи), но очереди на один плагин из двух процессов не будет.

## 3. Целевой дизайн

### 3.1 Принцип: проект — параметр ВЫЗОВА (не процесса)

* Новый необязательный параметр `project` у адресных инструментов. Принимает:
  `(ReaProject*)0x…` (поинтер), GUI-индекс, имя файла (`.rpp` опционально).
  **`None` (по умолчанию) = текущая вкладка = сегодняшнее поведение** (совместимость).
* Внутри: resolve → поинтер (`reapy.Project(project)`), затем **проверка живости** перед каждым
  шагом записи: поинтер всё ещё в списке `EnumProjects`; расхождение — типизированный отказ
  (`StaleProject`), а не запись наугад.
* Контекст на время вызова: `contextvars.ContextVar` (вызовы в одном процессе сериализованы —
  измерено; contextvar переживёт и будущий async). Установка на входе обёртки инструмента,
  сброс в `finally`.

### 3.2 Контроллеры

* `BaseController._project()` — единственная точка: contextvar → `reapy.Project()`, иначе
  `reapy.Project(project)`. Заменить **66** вызовов `reapy.Project()`.
* `utils/position_utils.py` (4 вызова) — тот же резолвер (или явный параметр).
* `master_controller` — мастер **пер-проект**; вызовы без `project` берут текущий (как сегодня).

### 3.3 Плагиновый слой

* `host/reaper.py`: `GetTrack(0, i)` → `GetTrack(self._project_handle, i)` — **2 строки** (677, 729),
  плюс протаскивание поинтера в мост (мост создаётся на вызов).
* `PluginInstanceRef.location` получает компоненту проекта (например `project`: поинтер или
  стабильный id) → **токены и evidence разделяются по вкладкам**; `FxHostFacts` — то же поле.
* Профиль/фингерпринт НЕ меняется (identity — от плагина), кэш профилей общий (это ок).

### 3.4 Инструменты

Новые (2, read-only + переключение):

| инструмент | что делает |
|---|---|
| `list_project_tabs()` | вкладки: index, pointer, file, name, `is_current`, track_count. Переиспользует `_open_projects()` |
| `select_project_tab(project)` | переключение через `SelectProjectInstance`; проверка ДО/ПОСЛЕ через `EnumProjects`, в ответе — что было и что стало |

Изменяемые (параметр `project`):

* все адресные семейства: track / fx / item / marker / midi / audio / master (везде, где есть
  `track_index` или `fx_index`);
* плагиновые: `instance`/`location` принимают компоненту проекта (или отдельный параметр `project`);
* `preset_*` (track+fx) — `get/set/navigate/save_fx_preset`;
* `save_project` — адресовать проект через `Main_SaveProjectEx(proj)` (пинуется, измерено).
* `apply_audiocpp_manifest` — уже имеет `project_id`; после фазы 1 — протащить проект в контроллер
  (закрывает § 1.3 полностью).

### 3.5 Глобальные операции: «блокировка → переключение → операция → возврат → разблокировка»

Операции, которые REAPER выполняет только на текущей вкладке (рендер 42230; `new_project_tab`;
будущее закрытие вкладки):

1. **acquire** — внутри процесса: мьютекс; между процессами: `SetExtState` в самом REAPER
   (секция `reaper_reapy_mcp`, ключ `global_lock`) со значением `{pid, task_id, utc, project}`.
   Staleness: возраст > N минут или мёртвый pid на этой машине → освобождение **с записью в ответ**
   (никогда не «молча отобрать у живого»).
2. **прочитать текущую вкладку** (`EnumProjects(0)`).
3. **select target** — `SelectProjectInstance(target)`; verify: `EnumProjects(0)` == target.
4. **операция** (например рендер).
5. **restore** — вернуть вкладку из шага 2; verify.
6. **release** — в `finally`, чтобы исключение и модальное окно REAPER не оставляли лок навсегда.

В ответе: какой таб стал текущим, что рендерилось, вернулся ли предыдущий, сколько держался лок.
Если замер п. 6.1 подтвердит `Main_OnCommandEx(42230, 0, proj)` — шаги 2–5 не нужны для рендера,
лок остаётся только против «двух одновременных глобальных операций».

### 3.6 Совместимость

* `project=None` = сегодняшнее поведение; старые вызовы (в т.ч. все 90 тестовых мест `location`)
  не меняются при необязательном поле.
* Счётчики инструментов сдвинутся (+2; пины в `tests/plugins/test_p0_contracts.py` и доки
  `06-mcp-tool-contracts.md`, `13-existing-mcp-integration.md`).

## 4. Риски и их закрытие

| риск | закрытие |
|---|---|
| вкладку закрыли/переставили под работающим вызовом | re-verify поинтера перед КАЖДОЙ записью; отказ `StaleProject`, никогда не «следующая похожая вкладка» |
| имя как ключ | только для сохранённых (сегодня 3 из 4 вкладок без имени — измерено); основной ключ — поинтер, имя — удобный синоним |
| два процесса одновременно переключают вкладки | только ExtState-лок; иначе агент A вернёт вкладку B на свою |
| модальные окна REAPER (рендер, измерено в `render_project`) | лок снимается в `finally` + staleness; рендер и сейчас обёрнут защитой от «Nothing to render» |
| коллизия токенов между вкладками | проект в `location` (фаза 2) ДО включения параллельной работы |
| undo на чужой вкладке | `Undo_BeginBlock2(proj)` принимает проект — замер (п. 6.4), затем по результату |

## 5. Фазы (каждая заканчивается оффлайн-тестами и коммитом)

* **Ф0 — мелкий фикс, независим от всего.** Манифест: сверять `EnumProjects(0) == project.id` на
  границах (до первой записи и после каждой ступени) и отказывать при расхождении — пока (после Ф1)
  проект не будет протащен в контроллер целиком.
* **Ф1 — адресация.** contextvar + параметр `project`; контроллеры (66) + `position_utils` (4);
  `list_project_tabs` + `select_project_tab`; `save_project(project)`. Оффлайн: резолвер, отказы,
  форму адресов; живой (read-only): чтение чужой вкладки через продукт.
* **Ф2 — плагиновый слой.** Поинтер проекта в мост (2 строки), проект в `location`/`FxHostFacts`,
  разделение токенов/evidence. Оффлайн: два токена для двух вкладок; живой: запись в НЕ-текущую
  вкладку и её проверка (`plugin_write` + read-back).
* **Ф3 — глобальный лок + рендер.** Сначала замер 6.1 (может упростить до «лок без переключения»);
  затем лок, отчёт, `finally`. Оффлайн: локи/staleness на фейковом ExtState; живой: рендер чужой
  вкладки, отчёт «что переключалось».
* **Ф4 — доки и приёмка.** Контракты, пины, README серии; живой прогон «два процесса, две вкладки,
  одновременная работа, ни одной записи не туда» с числами в `IMPLEMENTATION-STATUS.md`.

## 6. Что замерить ДО кода (живьём, по порядку)

1. **`Main_OnCommandEx(42230, 0, proj)`** — рендерит ли ЧУЖУЮ вкладку без переключения? Если да —
   весь пункт «переключать → рендерить → возвращать» для рендера не нужен (лок остаётся).
2. **Запись чанка в НЕ-текущий проект** (`write_state_slice`-тракт): чтение доказано, запись — нет.
3. **`Main_SaveProjectEx(proj)`** на не-текущем проекте (мутация — нужно ОК владельца).
4. **`Undo_BeginBlock2(proj)`/`Undo_EndBlock2`** на не-текущем.
5. **Закрытие вкладки под работающим вызовом** — какие именно ошибки приходят (чтобы отказ был
   типизирован, а не случайным).
6. **`SelectProjectInstance(ptr)`** — переключает ли вкладку (визуально/по `EnumProjects(0)`), что
   возвращает, и что при уже-текущей; возврат назад тем же вызовом.
7. **ExtState через reapy**: `Set/Get/DeleteExtState` из одного процесса и из двух; измеренная
   задержка; поведение при незавершённой записи.
8. **Два процесса одновременно**: чтения/GetTrack не конфликтуют; verify-on-write ловит чужую
   правку (ожидание: отказ `TargetChanged`/несовпадение, без порчи).
9. **EnumProjects**: имя сохранённой/несохранённой вкладки стабильно между вызовами (частично
   уже измерено: сохранённая → полный путь, несохранённая → пусто).

## 7. Открытые вопросы к владельцу

1. `project` — во ВСЕХ адресных инструментах или только в «горячих» (трек/FX/плагин/пресет)?
   Предложение: везде, где есть `track_index`/`fx_index`, + инструменты уровня проекта.

4. Нужны ли `open_project(file)` (есть `Main_openProject`) и `close_project_tab` (есть действие
   40860) как инструменты — или это остаётся ручной работой?
5. Мастер-трек: подтверждаем «мастер пер-проект, вызов без `project` = текущая вкладка»?

## 8. Чеклист «готово, когда»

* [ ] два агента (два процесса/окна) одновременно пишут каждый в свою вкладку; ни одна запись
      не ушла не туда (verify на каждой; отчёт с числами);
* [ ] один агент работает в двух вкладках по параметру `project`, без переключений GUI там, где
      они не нужны;
* [ ] рендер: чужой проект рендерится без порчи работы соседа; в ответе — что переключалось,
      вернулось ли, сколько держался лок; лок снимается даже при ошибке/модальном окне;
* [ ] манифест: `project_id` пинует ВСЁ, включая записи через контроллер (§ 1.3 закрыт);
* [ ] оффлайн: сегодняшние тесты зелёные + новые (резолвер, отказы, токены, лок);
* [ ] доки: контракты и пины обновлены; живой приёмочный прогон записан в `IMPLEMENTATION-STATUS.md`.
