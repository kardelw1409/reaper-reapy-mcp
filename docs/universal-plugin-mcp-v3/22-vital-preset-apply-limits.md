# 22. Vital preset apply: what carries fully, what does not, and how wavetables load

Дата: 2026-10-17. Автор: P38 (первая редакция) + **P39 (обновление: механизм найден, таблицы
грузятся)**. См. журнал `IMPLEMENTATION-STATUS.md` §39 и §40.
Все числа — из живых замеров на инстансе Vital VST3i **1.5.5** (трек 15 / индекс 14);
evidence каждого прогона лежит в `%LOCALAPPDATA%\reaper_reapy_mcp\run_artifacts\…__vital-preset-research__*`
(P32: в репозиторий evidence не попадает). Репозиторий хранит инструменты и записи, не их вывод.

> **P39 (главное).** Правило, которое P38 измерил как «рост ≤ 32 символов доезжает», объяснено
> полностью: запись state ложится **iff новый документ длиннее текущего не более чем на ~32 символа**
> — это хвост вокруг документа внутри состояния плагина, а не свойство таблиц. Поэтому таблица,
> которая растит документ сильнее, теперь доставляется **в две записи**: сначала слот надувается
> «баллоном» (плагин ре-сериализует каждый стаб-кейфрейм как ПОЛНЫЙ кадр, состояние становится больше
> таблицы), затем таблица пишется как **сжатие**, а сжатие ложится всегда. Измерено живьём на таблице
> 16 кадров / 175 497 Б и принято на продуктовом пути (`plugin_presets(op="apply")`) с таблицей
> 8 кадров / 87 856 Б. Guard больше **не** отказывает растущей таблице: `wavetable_growth_refused`
> в §4 заменён на `wavetable_unwritable` (отказ по СОДЕРЖИМОМУ, не по размеру).

Документ отвечает на один вопрос: **если я попросил `plugin_presets(op="apply", preset=…)`, что именно
из этого пресета окажется в плагине — и что будет молча не так.**

## 1. Три исхода применения (и как их увидеть в ответе)

Ответ инструмента — schema-2 конверт. Признак «пресет лёг не весь» — `partial: true` плюс блок
`preset_carry {gaps, reasons}` и список `gaps[]`, где каждый не перенесённый кусок назван с причиной.

| исход | что это значит | как видно |
|---|---|---|
| **ложится целиком** | контролы, элементы (`lfos`, `custom_warps`, `random_values`), метки, сэмпл, маршруты, которые билд принимает, и **таблица** — с P39 растущая таблица тоже ложится (в две записи, §2) | `verdict=ALL_VERIFIED`, `partial` покрыт необязательными gap'ами (см. ниже) |
| **ложится частично** | часть пресета не может быть перенесена этим каналом; остальное применяется и проверяется | `partial: true`, каждый `gaps[].reason` из таблицы §4 |
| **отказывается целиком** | правило зависимостей или ошибка — транзакция откатывается к захваченному состоянию | `ok: false`, `error.code`, `outcome.verdict` из `FAILED_*` |

Даже «частично» — это **проверенный** результат: каждый юнит записи читается назад и сравнивается,
а `outcome.channels` содержит построчную таблицу «записано / прочитано / совпало».

## 2. Таблицы (wavetables): измеренный масштаб проблемы

`.vital`-файл несёт до трёх wavetable-слотов (`settings.wavetables[]`), каждый — группы компонентов
с кадрами (`keyframes[].wave_data`, base64 float32, 2048 сэмплов на кадр). **Много-кадровая таблица**
— это и есть «3D»/спектральная: `Oscillator N Wave Frame` (и маршруты на него) двигает движок по
кадрам.

**Стратифицированная выборка библиотеки** (`probe_p38_wavetable_corpus.py`, run
`20261017T201813Z__vital-preset-research__17008`; 150 файлов, шаг 14 по списку, отсортированному по
размеру — то есть выборка покрывает корпус, а не только крупные файлы):

| измерение | значение |
|---|---|
| файлов в библиотеке | 2226 (2.19 ГБ) |
| в выборке | 150 |
| все слоты = Init-таблица (применяются без потерь по таблицам) | **23 / 150** |
| несут минимум одну **кастомную** таблицу | **127 / 150 (85 %)** |
| кастомных таблиц в выборке | 246 |
| из них одно-кадровых / много-кадровых («3D») | 123 / **123** |
| **проходят guard** | **6** |
| **отклоняются** | **240** (в том числе **все 123 много-кадровых**) |
| payload кастомной таблицы: min / медиана / max | 649 / **87 856** / 1 469 727 Б |
| измеренно-безопасный payload (`VERIFIED_PAYLOAD_BYTES`) | **11 159** Б |

Прошедшие шесть — одно-кадровые таблицы, чей payload **ровно равен** Init-размеру (11 149–11 159 Б):
замена равной длины, а не рост. Так выглядела старая защита (`wavetables.py::check_writable`):
не расти ни в кадрах, ни в total samples, ни в content-bytes, ни в payload; при неизвестном
текущем слоте — не превышать измеренно-безопасный размер. **P39 эту защиту отменил** (§2.1):
она была обходным путём вокруг фреймингового ограничения, а не измеренным свойством таблиц.

### 2.1 Как таблица доставляется с P39

1. **Измеренный закон канала.** Запись state ложится тогда и только тогда, когда новый документ не
   длиннее того, что держит хост, более чем на `headroom = len(item B) − 8 − конец JSON`. В каждом
   измеренном состоянии это **32 символа** (хвост вокруг документа). Патч собственных полей длины
   item B **не** сдвигает границу — хост пользуется своей запомненной длиной, а не полем в
   присланном тексте (проверено: поля правились, запись всё равно игнорировалась).
   Лестница на обычных строках: +8/+16/+24/+31 ложатся, **+32 ложится ровно на границе**, +33/+40/+64
   игнорируются (состояние остаётся побайтово прежним).
2. **Баллон.** Плагин ре-сериализует **каждый** wavetable-кейфрейм как полный кадр
   (`WaveSourceKeyframe::jsonToState`: декод в блок размером в кадр и `memcpy` целого кадра — тот же
   путь, которым живая проба записала 44-символьный payload и прочитала 2048 сэмплов). Поэтому
   таблица, записанная многими стаб-кейфреймами, **сжимается при записи** и читается назад
   большой. Ход: слот надувается баллоном (короткая запись, ложится), затем настоящая таблица пишется
   как **сжатие** — а сжатие всегда ложится.
3. **Что именно ставится баллоном.** Текущая (живая) таблица слота с её кейфреймами, заменёнными на
   K стаб-кейфреймов; payload стаба — первые сэмплы **той самой** таблицы, которую доставляем (не
   выдуманная волна). K выбирается так, чтобы комната `K × 10 924` покрывала размер таблицы.
4. **Проверка баллона — по ЭФФЕКТУ, не по равенству.** Read-back баллона — это пере-сериализация
   плагина (K полных кадров), поэтому сравнивать его с записанным нельзя; проверяется, что комната
   в read-back не меньше таблицы, которую он расчищает. Баллон — отдельный юнит в отчёте
   (`kind: balloon`) и отдельная строка в логе.

**Измеренные числа P39** (пробы `probe_p39_wrapper_sizes.py`, `probe_p39_balloon.py`,
`probe_p39_table_balloon.py`, приёмка `probe_p39_acceptance.py`):

| замер | результат |
|---|---|
| граница роста на живом состоянии | +31 ложится, **+32 ложится на границе**, +33 игнорируется |
| патч полей длины item B (+0x00 LE, +0x1C BE) | **не помогает** — граница не сдвинулась |
| баллон на слот (20 стаб-кейфреймов, запись 1 719 симв.) | лёг; read-back = 20 × 2048 сэмплов, **nan = 0, inf = 0** |
| таблица 16 кадров / 175 497 Б после баллона | **ложится как сжатие**, `table_id` совпал, документ = захват + слот |
| приёмка через `plugin_presets(op="apply")` | `ALL_VERIFIED`, таблица 8 кадров / **87 856 Б** в инстансе, `table_id` = файла, строка баллона: 9 кейфреймов → комната 98 804 симв. |

**Что слышит пользователь.** Пресет, опирающийся на свою таблицу, теперь звучит как **своя**
таблица: `wavetables_requested` = сколько слотов в файле, `wavetables_declined` = сколько из них
нечего писать (в значении нет никакого источника волны — такой слот звучит тишиной; либо в живом
документе нет `synth_version` для штампа `version`). РАЗМЕР таблицы причиной отказа больше не
является. Случай `House Bass` (SNFK), который P38 привёл как пример потери таблицы, доставляется
целиком.

### 2.2 Слот `Audio File Source` — на чём построено семейство гроулов

Офлайн-обзор семейства (`_p39c_family_survey.py`, 2026-10-18): запрос по именам/стилям
(`growl|wobble|dubstep|riddim|tearout|monst|bass|drop|sub`) даёт **536 пресетов**, из них **449 с
кастомной таблицей**, медиана максимального payload — **164 353 Б** (вдвое больше медианы P38-выборки),
максимум — **1 469 727 Б**. И большинство этих таблиц — **не** `Wave Source`: их источник — компонент
`Audio File Source`, у которого вся волна лежит в ОДНОЙ строке `audio_file` (base64 int16 PCM).
Плагин называет десять типов компонентов (`wavetable_component_factory.cpp`), из них **четыре —
источники**: `Wave Source`, `Line Source`, `Audio File Source`, `Shepard Tone Source`.Guard до этого
раунда знал только первый — то есть **отказывал именно той части гроула, которая делает его гроулом**.

Что измерено и что теперь делается:

| вопрос | ответ |
|---|---|
| опознание | `source_types`/`carries_waves` в `describe`; `audio_chars`/`audio_samples` для аудио-слота; `table_id` теперь дайджест **всех** источников (ключевой дайджест `Wave Source` не изменился — записанные с P30 id остаются верными) |
| доставка | тот же баллон: стаб-`Wave Source` **заменяет первый источник любого типа** (у аудио-слота он выбрасывает ~1.4 МБ audio — поэтому запись баллона — сильное сжатие), модификаторы графа сохраняются |
| потолок | из свежего Init-слота один баллон покрывает таблицу до **~2.4 МБ** (136 стаб-кейфреймов ≈ 1.5 МБ комнаты; потолок 256 кадров = 2.8 МБ). Максимум семейства (1.47 МБ) влезает с запасом; что не влезает — gap `no_room_for_growth`, а не догадка |
| проверка | аудио-payload сравнивается **полосой**, а не байтами: измерено (дважды на одной таблице 1 409 808 Б) — **8 856 из 528 388 сэмплов (1.676 %) возвращаются сдвинутыми ровно на 1 шаг** (`histogram {1: 8856}`), потому что плагин конвертирует int16 → float на загрузке и обратно на сохранении. Всё остальное (граф, кадры, окна, `version`) — точно; длина payload — всегда точно. `table_id` у аудио-слота поэтому НЕ совпадает байт-в-байт, и строка отчёта это прямо говорит (`table_id_agrees_note`) |
| что слышно в окне баллона | слот несколько секунд держит стаб (первые сэмплы **самой доставляемой** таблицы, а не шум), затем в него пишется таблица. Прошлая таблица в этом окне не звучит |

**Живая приёмка (2026-10-18, продуктовый путь `plugin_presets(op="apply")`):**

| пресет | результат |
|---|---|
| `CH - Future Bass Super Saw 4` (Wave Source, 8 кадров / 87 856 Б) | `ALL_VERIFIED`, `table_id` = файла |
| `Dubstep Growl Seq` (`Audio File Source` ×3: 1 409 791 + 1 409 808 + 86 997 Б) | `ALL_VERIFIED`, **`wavetables_requested: 3`, `wavetables_declined: 0`**, все три слота несут файл: сэмплов 528 388 / 528 388 / 32 429, баллоны 130 / 130 / 8 кадров, у третьего слота `table_id` совпал байт-в-байт |

**Пакетный прогон по семейству** (`probe_p39h_family_batch.py`, 2026-10-18, шесть применений подряд
через продуктовый путь, evidence `…20261017T224335Z__vital-preset-research__21216`):
| пресет | слоты в файле / принесено | время |
|---|---|---|
| `BASS Broken Circuit` (аудио-**1 469 727 Б** — максимум семейства) | **3 / 3** | 89.0 s |
| `Dubstep Growl Seq` | **3 / 3** | 59.7 s |
| `Vain Bass` (аудио 1 409 788 + Wave Source 8 кадров) | **3 / 3** | 54.9 s |
| `Grote` (аудио 150 832 + Wave Source 2 кадра) | **3 / 3** | 45.2 s |
| `BASS - Deep 2` (аудио 164 353) | **3 / 3** | 71.4 s |
| `Growl` (Wave Source 16 кадров / 175 497 + аудио 841 563) | **3 / 3** | 80.8 s |

**Итог: 6/6 применений `ALL_VERIFIED` и committed, 18 из 18 слотов несут файл.** При этом в 16 из 18
случаев `table_id` совпал **байт-в-байт** (включая самый большой аудио-слот): реквант срабатывает не
всегда — зависит от значений сэмплов, — а там, где сработал (`Dubstep Growl Seq`, слоты 1 и 2),
строка отчёта прямо говорит, что id сравнивать нельзя, и даёт полосу. Оставшиеся gap'ы — те же, что и
в P38, и к таблицам не относятся: `host_owned_parameter` (темп), `guarded_rule_subject`
(`fm_needs_modulator`), `destination_dropped_by_plugin` (билд выбрасывает имя destination'а),
`slot_text_dropped_with_pair`, `growth_over_budget`, `sample_growth_over_budget`.

**Коварный случай (подтверждён приёмкой P39).** `LD - Future Saw` (Florixel) **вообще не несёт
кастомных таблиц** — все три слота Init, а файл меняет **30 контролов** (компрессор, EQ, `filter_fx`,
реверб, volume, polyphony, portamento) и оставляет все `osc_*` на Init. Он применяется **полностью и
верно**, но звучит как инитовский пилообразный тон — потому что он таким и является. Приёмка P39
подтвердила это с другой стороны: применение этого пресета записало Init-таблицу
(`table_id 1e4f3dfee12a65b88d98`, 1 кадр / 2 048 сэмплов / 11 159 Б) во все три слота — то есть
«инит-пила» пришла из файла, а не из сломанной записи. Отличить одно от другого можно только
сравнением с Init-состоянием: см. §3.

### 2.3 🔴 Потолок размера состояния: ~4 МБ текста блока

Баллон делает состояние плагина большим, и у этого есть жёсткий предел — измеренный 2026-10-18:

| факт | число |
|---|---|
| состояние, при котором инстанс стал НЕЧИТАЕМЫМ | `item B` = **3 363 963 Б** (≈ 2.52 МБ JSON), текст блока = **4 485 284 симв.** |
| что делает хост при чтении | `OSError: exception: access violation writing 0x…` — ёмкости 4.4/5/6/9/20 МБ падают; ёмкость 4.0/4.1 МБ отдаёт **обрезанный** чанк |
| это про состояние, а не про буфер | те же ёмкости читают лёгкие дорожки (0/1) без ошибок |
| принятый ранее `Dubstep Growl Seq` (три таблицы, 2.91 МБ) | текст блока ≈ **4.0 МБ — чуть ниже линии**; читался многократно и нормально |

Вывод: линия лежит между **4.0 и 4.45 МБ текста блока** (≈ 3.0–3.3 МБ состояния JSON), и пресет
масштаба «три таблицы по 1.4 МБ» стоит ровно на ней — он прошёл, но **без запаса**. Поэтому
планировщик держит консервативный потолок (на момент этого замера — `4 000 000` текста минус 250 КБ
запаса → 2.81 МБ состояния; окончательные константы после второй серии проб — в §2.3.1) и отказывает
записи, которая его перейдёт, называя причину `state_ceiling_reached` вместе со спроектированным и
допустимым размером. **Цена отказа:** самые большие трёхслотовые пресеты семейства могут не поехать —
зато инстанс остаётся читаемым, а читаемость и есть то, без чего слой не умеет ни верифицировать, ни
откатывать.

Раньше этот же сбой слой принимал за потерю транспорта (`NotConnected`) и **повторял** его; теперь он
классифицируется как `Unreadable` с причиной `state_too_large_to_read` и не ретраится.

#### 2.3.1 Границы уточнены прямыми пробами (2026-10-18, вторая серия)

Две константы выше были оценкой по двум точкам. Серия проб, которая писала в инстанс документ
РОВНО заданного размера и читала его обратно, сузила зазор:

| состояние (симв. JSON) | текст блока | результат чтения |
|---|---|---|
| 3 048 249 | 4 083 632 | **прочитано целиком** (устойчиво на всех ёмкостях ≥ длины) |
| **3 127 179** | **4 189 248** | **прочитано целиком** — это и есть самый большой измеренный успех |
| **3 166 642** | ≈ 4 240 000 | `Unreadable` — падение на чтении |
| 3 206 106 | ≈ 4 290 000 | `Unreadable` |
| 3 363 963 | 4 485 284 | `Unreadable` (три прогона подряд) |
| любая ёмкость НИЖЕ реальной длины | — | ровно `capacity − 1`, т.е. **обрезанный** чанк |

Зазор сузился с «4.08 … 4.45» до **«4 189 248 читается, 4 240 000 — нет»**. Потолок выставлен по
самому большому измеренному успеху с запасом ~100 КБ текста:
`STATE_CHUNK_CEILING_CHARS = 4 100 000` минус `25 000` запаса → **3 056 250 символов состояния**
(шаг расширения 4/3). Обе стороны закреплены тестом (`test_p39c_audio_slots.py`): читаемое состояние
обязано быть разрешено, а падающее — отказано. Так будущая правка не сможет тихо вернуть линию к
догадке.

**Как выйти, если такой инстанс всё-таки получился** (слой его не прочтёт и не восстановит —
`SetTrackStateChunk` идёт с `isUndo=False`, так что Ctrl+Z не поможет): открыть в самом плагине
браузер вейвтейблов и загрузить обычную таблицу (или пресет) — плагин сам уменьшит своё состояние;
либо удалить и заново добавить инстанс; либо откатить проект к файлу на диске. **Обрезанный чанк
записывать обратно нельзя** — это потеря пресета, а не лечение.

### 2.4 Сэмпл-блок: доставка двумя записями

Замерено на двух реальных пресетах семейства: `BASS Broken Circuit` — сэмпл растёт на **99 508**
символов, `BASS - Deep 2` — на **132 300**, и он **стерео** (два payload'а). Ни один не ложится одной
записью. Первая попытка — занять комнату баллоном вейвтейбл-слота — **не работает** (проверено живым
прогоном): рост сэмпла есть рост всего документа, а инфляция слота эту комнату уже израсходовала.
Работает другое: **сэмпл надувает себя сам** — блок переобъявляется с большим `length` и крошечным
payload (запись сжимается → ложится), плагин пересорит столько сэмплов, и payload файла приезжает
как сжатие этого. Две записи идут подряд, потому что любой другой юнит документ сжимает и комнату
забирает. Верификация теперь применяет полосу сэмпл-канала (измеренная задержка 4 сэмпла) к
**каждому** payload'у блока — `samples` **и** `samples_stereo`; проверка только первого отказывала
стерео-записи, у которой комната на самом деле была.

Проверка: `BASS - Deep 2` через продуктовый путь — `ALL_VERIFIED`, `sample: 1`, имя / длина / размер
блока совпали с файлом (`Drone Stab`, 93 712 сэмплов, 249 900 символов), из gap'ов остался только
`host_owned_parameter`.

#### 2.4.1 🔴 Копия того, что прочитал, дрейфует: payload едет по 4 сэмпла за запись

Второй, куда более неприятный эффект той же задержки — и он бил не по доставке, а по ВЕРНОСТИ
волны. Механика: плагин отдаёт PCM на 4 сэмпла позже (`SAMPLE_RELOAD_DELAY`, тот же
`Sample::jsonToState`), а каждый следующий юнит транзакции шлёт документ ЦЕЛИКОМ — тот, который
только что прочитан. То есть каждая последующая запись отправляла уже сдвинутый payload и сдвигала
его ещё раз.

Измерено живьём: у `BASS - Deep 2` имя и длина совпали с файлом, а **99.6 % сэмплов отличались** —
это оказался payload файла, задержанный на **48 сэмплов = 12 × 4**, ровно по числу записей
после сэмпла. Каждая отдельная запись была в полосе задержки, поэтому поверная верификация юнита
этого не видела: расхождение накапливалось МЕЖДУ юнитами.

Починка — «carry намерения» в транзакции: юнит собирается не из read-back, а из read-back, в
который возвращены значения, которые эта транзакция УЖЕ записала (`Transaction._intended` +
`VitalCodec.apply_intended_values`); пути, которые пишет сам юнит, carry не трогает, поэтому
поздний юнит всегда побеждает.

**И один баг внутри починки, найденный контрольным тестом** (потому что «тест, который не может
упасть» — не доказательство): carry применялся к ОБЁРТКЕ `decode()` (`{"document": …, …}`), а не к
самому документу, так что `set_path` добавлял лишний ключ верхнего уровня и молча ничего не делал —
дрейф оставался. Теперь `apply_intended_values` разворачивает обёртку так же, как `encode_slice` и
`snapshot_document`, и тест ходит через ту же форму, которую транзакция реально передаёт.
Остаточная задержка ровно **одна** (4 сэмпла) — это собственная задержка плагина, её и показывает
полоса верификации.

#### 2.4.2 Сэмпл-пара идёт по РАСПИСАНИЮ, а не первой

`BASS Broken Circuit` отказывал своему сэмплу (`no_room_for_sample_growth`) ровно потому, что пара
«надуть — записать» стояла ПЕРВОЙ: она встречала документ, ещё державший три больших таблицы
предыдущего пресета. А сам пресет через пару юнитов СЖИМАЕТ две из них (1 409 791 и 86 997 → 11 149
байт каждую, ~1.5 МБ свободного места).

Теперь план не фиксирует порядок, а **симулирует три кандидата** (рост по возрастанию, накладные
расходы по возрастанию, по убыванию) и берёт тот, у которого пик документа ниже; равенство
разрешается в пользу первого кандидата, поэтому выбор детерминирован. Всё это арифметика над
измеренными числами: размер живого документа, точный размер цели и `room_chars` баллона известны до
записи.

**Живой результат (2026-10-18, шесть пресетов семейства подряд, тёплый инстанс):** 6/6
`ALL_VERIFIED`, **6/6 сэмплов** (было 4/6) и 17/18 слотов — единственный отказ это первый слот
`Dubstep Growl Seq`, у которого собственные три таблицы ~2.9 МБ, и он наткнулся на потолок при уже
занятом инстансе (`state_ceiling_reached`, назван; на свежем инстансе тот же пресет въезжает 3/3).

## 3. Как заранее понять, приедет ли пресет целиком

Практическая последовательность (все — существующие инструменты, ничего дописывать не нужно):

1. `plugin_presets(op="search", query=…, style=…)` — найти кандидата;
2. `plugin_presets(op="apply", dry_run=true, preset=…)` — посмотреть `counts` и `gaps`:
   * `counts.wavetables_requested` / `wavetables_declined` — сколько слотов пресет несёт и сколько
     из них отказано (в примерах выше: 3 запрошено / 2 и 1 отказаны);
   * `counts.routes_skipped_known_drop`, `gaps[].reason` — что ещё не поедет (§4);
3. если таблица критична — размер больше не преграда (P39 §2.1): растущая таблица едет в две записи,
   а «сколько слотов в файле и сколько из них отклонено» видно в
   `counts.wavetables_requested` / `counts.wavetables_declined` (отказ теперь означает «в файле нет
   кадров» либо таблицу выше того, что можно расчистить — 256 стаб-кейфреймов, ~2.8 МБ);
4. после реального применения — сверить документ с файлом (это делает приёмочная проба
   `probe_p38_apply_timed.py`: `comparison.controls_equal` / `mismatch`, `labels_ok`).

Полезно знать: «тонкость» пресета (сколько контролов он реально меняет относительно Init) — не
дефект применения. `LD - Future Saw` меняет 30 контролов, `BASS Bizzare Future` — 140; оба корректны в
своих пределах.

## 5. Что в этой области **не** проверено (и не должно читаться как «работает»)

1. **Форма границы записи — ИЗМЕРЕНА (P39).** P38 видел симптом (одна и та же дельта блока `+44`
   при росте значения на 32 и на 33), P39 нашёл причину: запись ложится iff документ не длиннее
   прежнего более чем на 32 символа — хвост вокруг документа внутри состояния плагина. Проверено
   лестницей на обычных строках (при той же дельте блока), патчем полей длины
   (не помогает — см. §2.1) и финальной доставкой таблицы в две записи. Что при этом осталось
   без объяснения и честно померено: **байты за пределами записанного payload баллона** — это
   предвыделенный буфер кадра (`MemoryOutputStream(sizeof(float) * kWaveformSize)`), на живом билде
   они оказались конечными (nan = 0, inf = 0, пик ~3.3e35) и живут только внутри того слота,
   который в этой же транзакции заменяется; отдельного пути без баллона (например, через нативное
   меню пресетов хоста) не искали.
1a. **Баллон громко/тихо.** Слот на время баллона звучит стабом (первые сэмплы доставляемой
   таблицы) — это транзиентное, секунды, но **на слух не измерялось**: проба слышит только то, что
   видно в документе. Также не проверялось, как поведёт себя плагин, если между двумя записями
   пользователь нажмёт что-то в его UI: слой защищён от внешнего ПИСАТЕЛЯ (ревалидация), но не от
   пользовательского клика.
1b. **`Line Source` и `Shepard Tone Source`.** Их присутствие считается волновыми данными
   (компонент-источник есть), но их payload слой НЕ разбирает и не сверяет: у `Line Source` это
   генератор (`num_points`/точки), у Shepard — свои поля. В обследованном семействе таких таблиц не
   встретилось; если встретится, верификация будет сверять граф точно, а содержимое источника —
   только по факту наличия.
1c. **Полоса рекванта аудио — детерминированная, но узкая по замерам.** Две пробы на одной таблице
   дали одинаковые 8 856/528 388 с максимумом 1 шаг; на другой (86 997 Б) аудио вернулось
   байт-в-байт. От чего зависит — от значений сэмплов (точность float) — не исследовалось; поэтому
   полоса фиксирована как «длина точно + шаг ≤ 1», а не как доля.
1d. **Баллон сэмпла — измерен на двух пресетах, не на семействе.** `BASS Broken Circuit` (моно) и
   `BASS - Deep 2` (стерео) прошли; суждение «комнату сэмплу не даёт баллон слота» — из живого
   прогона, где сэмпл не поехал при уже надутом слоте. Худший случай (сэмпл на пределе
   `kMaxSize = 1 764 000` сэмплов) не гонялся: планировщик его отказывает, но отказ наблюдался
   только на офлайн-хосте.
1e. **Потолок состояния — граница в широком интервале.** Два наблюдения (не бисекция): 4.0 МБ текста
   блока — читается, 4.45 МБ — падает. Что именно делает хост на этой границе (обрезает буфер или
   отказывает в копировании) не выяснялось; поэтому зашит консервативный порог, а не измеренная
   точка. Прочитать застрявший инстанс обратно слой **не** умеет ни одним из путей, которые есть
   внутри процесс (см. §2.3 — выход только через UI плагина или откат проекта).

   | случай | рост JSON | рост значения | дельта блока | результат |
   |---|---|---|---|---|
   | один путь | +32 | 32 | +44 | **долетел** |
   | один путь | +33 | 33 | +44 | **не долетел** |
   | два пути | +33 (20+13) | ≤20 | +36 | **долетел** |
   | два пути | +40 (20+20) | 20 | +44 | **не долетел** |
   | два пути | +48 (20+28) | 28 | +56 | **не долетел** |
   | три пути | +56 (20+32+4) | ≤32 | +56 | **не долетел** |
   | сжатие (pad) 8…64 | ≤ 0 | — | 0 | **все долетели** |

   То есть лимит лежит по **JSON-тексту документа** — что и подтвердил P39, доведя до точного
   механизма (§2.1). Практический вывод зашит в коде: бюджет юнита = живой `headroom − 8`,
   а значение вне таблицы, чей рост выше бюджета, называется gap'ом.
2. **Юнит 34/38 тяжёлой цепочки — объяснён и исправлен.** Он падал на `modulation_35_amount`,
   `modulation_38_bipolar`, `modulation_41_amount` — то есть на полях **неактивных** слотов, чью пару
   плагин выбросил (§4). Теперь поля слота, чей маршрут не поехал, пропускаются вместе с ним
   (`slot_text_dropped_with_pair`). Повторный прогон той цепочки — следующий замер.
3. **Точная граница по типам записей.** Лестницы гонялись на строках (метки, `comments`); числовые
   значения не проверялись (их вклад — длина repr).
4. **Которые именно destination'ы билд принимает.** Профиль перечисляет 316 имён; часть из них этот
   билд выбрасывает. read-only канала для этого не найдено — узнаётся записью (мемо
   `vital_destination_drops.json` копит факты по билду). Первое применение всегда платит за
   неизвестность.
5. **Сэмпл: точная величина рекванта.** Три записи ложились с остатком 0, четвёртая дала 1060/44096
   сэмплов на ±1 LSB (2.4 %). Вердикт теперь принимает один шаг в пределах измеренной полосы, но
   почему реквант включается не всегда — не объяснено.
6. **`op="init"`** — типизированный отказ (`init_artifact_not_recorded`): Init этот билд строит в
   коде, измеренного артефакта нет.

2. ✅ **Юнит 34/38 объяснён и исправлен** (§5.2): поля слота, чей маршрут не поехал,
   пропускаются вместе с ним (`slot_text_dropped_with_pair`). Повторный прогон тяжёлой
   цепочки (38 юнитов) — следующий замер; он дешёвый и не требует ничего, кроме запуска.
3. **Сделать `partial` заметным**: сейчас «пресет приехал не весь» — это `partial: true` и строчка в
   `gaps[]`. Для пользователя это шум; стоит поднимать в ответе сводку «что не поехало» рядом с
   `counts` (и, возможно, отдельным `warnings[]` в конверте).
4. **Подсказать выбор пресета**: фильтр в `search`/`info` — «сколько слотов таблиц в файле и есть
   ли в них кадры»; размер таблицы при этом больше не критичен (P39), а вот «в файле нет кадров»
   остаётся реальной причиной расхождения с ожиданием пользователя.
5. **Показать баллон в dry-run**: сейчас `partial`/`gaps` не содержат ничего про две записи (юниты
   планируются уже после раскрытия запроса), а строка `kind: balloon` появляется только в отчёте
   реального применения. Дешёвая правка — считать план юнитов и на dry-run, чтобы ответ сразу говорил
   «таблица поедет в две записи».
6. **Арифметика потолка состояния** (следствие §2.3). Отказ `state_ceiling_reached` сейчас приходит
   уже после того, как пресет прочитан и сравнён; полезнее — показать его в `info` пресета («этот
   пресет спроектирует состояние на 3.2 МБ — выше потолка 2.81 МБ»). Тогда решение «грузить /
   поискать поменьше» принимается до первого сильного применения, а не после.
7. **Точка границы — биссекция.** Два наблюдения (4.0 МБ читается, 4.45 МБ падает) дают интервал, а
   не точку. Он стоит десятка применений одного и того же большого пресета с шагом по размеру — и
   позволил бы поднять потолок ближе к линии (то есть вернуть самые большие трёхслотовые пресеты).
