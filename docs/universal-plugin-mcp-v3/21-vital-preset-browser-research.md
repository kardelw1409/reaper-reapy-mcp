Одной фразой: **внутренний браузер Vital достижим только через файлы `.vital` и документ (state chunk);
host-API-пресеты REAPER к нему отношения не имеют** (все живые ответы пусты, §5), а «применение»
файла обязано идти нашим существующим chunk-каналом после того, как стадия B докажет эквивалентность
GUI-загрузке.

## 2. Как работает внутренний браузер (по исходникам)

Всё ниже — чек-аут 1.0.6; «эра» билда 1.5.5 помечена отдельно.

- **Корни поиска.** Каталог данных `getDataDirectory` (`src/common/load_save.cpp:1734`): ключ
  `data_directory`, иначе Windows `Documents\Vial` (в билде 1.5.5 — `Documents\Vital` [И]).
  `getDirectories` (`:1761`) даёт `<data>\Presets` + подкаталоги первого уровня с `Presets`
  (`findDirectories` depth 1), т.е. `User\Presets` — **дополнительный** корень, а не «тень»;
  `getAllUserPresets` (`:1871`) перечисляет оба. Файлы ищутся рекурсивно (`:1842`),
  расширение `kPresetExtension = "vital"` (`src/common/synth_constants.h:52`).
- **Поиск/фильтр.** `PresetList::filter` (`src/interface/preset_browser.cpp:380`): токены по **имени
  файла + author**; кнопки стилей сравниваются с `preset_style`. Комментарии в поиск не входят.
- **Словарь стилей.** Enum `PresetStyle` (`src/common/load_save.h:49`): Bass, Lead, Keys, Pad,
  Percussion, Sequence, Experimental, Sfx, Template; отображаемые строки `kPresetStyleNames`
  (`src/common/synth_strings.h:62`) — «Experiment», «SFX». В файлах корпуса встречаются ровно
  эти слова (§3) — значит поисковая категория читается прямо из `preset_style`.
- **Загрузка пресета в движок.** `SynthBase::loadFromFile` (`src/common/synth_base.cpp:354-380`):
  JSON парсится, `loadFromJson` → `LoadSave::jsonToState` (`src/common/load_save.cpp:1027-1054`),
  затем **`preset_name` перезаписывается именем файла** (`synth_base.cpp:372`) — встроенный
  `preset_name` только фолбэк. Заменяются: все controls (отсутствующие → дефолт), `modulations`
  (clear + перестройка), `sample`, `wavetables`, `lfos`, метаданные (`loadSaveState`), `active_file_`;
  звук глушится (`allSoundsOff`, `synth_base.cpp:342`). **Не заменяются**: tuning, MIDI-карта,
  sample rate/BPM [К]. Host уведомляется одним вызовом `updateHostDisplay()`
  (`src/interface/synth_editor.cpp:67`); имя для хоста — `getProgramName` → `getPresetName`
  (`src/plugin/synth_plugin.cpp:121`); MIDI program change игнорируется (`midi_manager.cpp:235`).
- **Обновление списка.** Собственное сохранение плагина обновляет браузер **немедленно**
  (`SaveSection::save` `src/interface/save_section.cpp:347` → `PresetBrowser::save` → `loadPresets`
  `src/interface/preset_browser.cpp:851,885` — полный rescan). **Внешний файл** (положенный в папку
  извне) — watcher'а/таймера нет; `visibilityChanged` делает только `redoCache` [К]. То есть
  «сохранить у нас на диске → показать в браузере» без действия пользователя не гарантировано.
- **Favorites.** `Vial.favorites` (`PropertiesFile`, app «Vial», `%APPDATA%\vial\`,
  `load_save.cpp:1165`), JSON-объект `{полный путь: 1}` (`addFavorite` `:1235`), пишется только
  кликом по звезде (`preset_browser.cpp:286-296`) [К]; на диске (билд 1.5.5) — `Vital.favorites`,
  1 запись-путь [И].
- **`Vital.library`** в чек-ауте не читается и не пишется [К]; в билде 1.5.5 файл есть и кэширует
  author/date/style (§3). **Это индекс UI-кэша, а не список пресетов**: он врёт относительно диска
  (4452/4451/2556 записей против 2226 файлов) [И] — наш каталог не должен ни читать его, ни пытаться
  «согласовать» с ним.
- **Банки `.vitalbank`.** Обычный ZIP (`ZipFile::Builder`, `src/interface/bank_exporter.cpp:575-629`),
  структура `<Name>/Presets|Wavetables|LFOs|Samples/**`, манифеста-JSON нет. Импорт распаковывает
  банк в каталог данных и помечает pack (`synth_preset_selector.cpp:318`) → `bankImported` → rescan →
  **пресеты банка появляются в браузере** [К]. На диске 6 `.vitalbank` [И].
- **Писатель файла.** `SynthBase::saveToFile` (`synth_base.cpp:547-565`): `JSON.dump()` без параметров —
  **одна строка**, ключи в **алфавитном порядке** (nlohmann `std::map`, `load_save.h:17`) [К]; перед
  записью имя пресета кладётся в `preset_name` (`:556`), каталог создаётся (`:550-553`).

## 7. Побочные эффекты и чего chunk-канал не воспроизводит

1. **`tuning` живёт только в документе** [И] и пресетом не заменяется [К]. При apply из файла
   документ надо собирать так, чтобы `tuning` (и любой другой документный, но не файловый ключ)
   сохранялся; иначе мы запишем документ без него и вся ответственность ложится на парсер плагина [П].
2. **GUI-состояние**: спектрограмма/редактор перерисуются по своим правилам; наш write-путь их не
   «дёргает» (host notify делает только сам плагин при своей загрузке) — [П], требует E-2.
3. **`sample` — lossy int16** (усечение, без дизера) [К]: применять пресет и **не сохранять** его
   обратно без нужды — иначе можно накопить потери; `preset_save` из живого документа пишет тот же
   lossy формат.
4. **Guard роста wavetable** (`VERIFIED_PAYLOAD_BYTES = 11 159`, отказ при росте frames/samples/
   content-bytes; один рост уже валил `reaper.exe`) [К/И P30]: apply пресета с более крупной таблицей
   будет **отказан guard'ом** — это защита, а не баг; для сценариев «взять пресет как есть» нужен
   либо более крупный измеренный предел, либо accept-with-refusal (S/M задача, не L).
   **Масштаб измерен 2026-10-17 (`probe_p38_wavetable_corpus.py`, 150 файлов стратифицированно):**
   23/150 пресетов состоят только из Init-таблиц (применяются полностью), **127/150 (85 %) несут
   кастомную таблицу; из 246 таких таблиц guard пропускает 6** (все — одно-кадровые с payload ровно
   размера Init, 11 149–11 159 Б), а **все 123 много-кадровые («3D») отклонены**; медианный payload
   кастомной таблицы — **87 856 Б**, максимум 1 469 727. Вывод: пресет, опирающийся на свою таблицу,
   прозвучит как таблица, уже лежащая в слоте (Init), при честном `partial: true` + gap
   `wavetable_growth_refused`. **Открытый вопрос (не приговор):** собственная загрузка плагина читает
   такие таблицы напрямую, а измеренная полоса роста (+44 долетает / +48 нет) имеет странную форму для
   «предела буфера» — объяснение через фрейминг/длины item-B **не проверялось**.
5. **Версии**: плагин отвергает пресет «новее» сборки [К] — при 77 файлах 1.5.x в корпусе это
   актуально только для старых инсталляций; обратный случай (1.0.x файл → 1.5.5) проходит через
   миграции, но **5 новых ключей 1.5.x получат дефолты** [П/К] — это ожидаемо, но должно попадать
   в план/отчёт `preset_apply`.
6. **Конкурентность**: пользователь грузит пресет в GUI во время нашей транзакции — наш слой уже
   умеет это ловить (token continuity + compare read-back) и откатывать [К `transaction.py`], но
   сценарий не проверялся живьём в режиме гонки — [П].
7. **Индекс `Vital.library` устаревает сам** (4452 записи против 2226 файлов) [И] — не использовать,
   не «починять»; свой индекс держать отдельно.
8. **GPL/бренд** (§1): не переносить код, не распространять free-пресеты, не трогать имена/сервисы.

## 8. Предлагаемая архитектура в нашем плагин-слое + каталог

**D1 — куда положить.** Не отдельный MCP-сервер (запрещено P26 Addendum 2 §1). Рекомендация:

- новый модуль провайдера `src/reaper_reapy_mcp/plugins/providers/vital/preset.py` — знание формата
  `.vital` (чтение/сборка/сравнение с документом), рядом с `wavetables.py`, который уже парсит
  пресеты («a .vital preset file is the SAME document», `wavetables.py:557`) [К];
- каталог — **вне** Capability Profile, со своим хранилищем и своей инвалидизацией (§ Addendum 2:
  Preset Catalog ≠ Capability Profile);
- tool-поверхность — **один новый инструмент** `plugin_presets` с `op`:
  `search|info|apply|save|init` (конвенция репо — один инструмент с op/mode: `plugin_state.op`,
  `plugin_prepare.mode`), а не 5 отдельных инструментов: +1 к 66-поверхности вместо +5;
  записывающие op (`apply`, `save`, `init`) обязаны быть объявлены в `SPEC["plugin_write"]`
  `mutating_ops` (`tools.py:133`) — сейчас там `(controls, routes_create, routes_update,
  routes_remove, state, wavetable)` [К] — и двигать `IMPLEMENTATION_REVISION` (`provider.py:156`) [К].
  Альтернатива (5 инструментов по именам контрактов Addendum 2) отвергнута: дороже для инструментного
  пикера и не даёт разделения, которого нет у op-параметра.
- `search`/`info` — read-only, доступны без write-профиля; `apply`/`save`/`init` — через
  `resolve._resolution(..., require_writable=True)` и существующий `Transaction` (dry-run → capture →
  apply → verify → rollback), т.е. «безопасность» не изобретается заново [К `transaction.py:176,496,635,1014,1101`].

**D2 — индекс пресетов.** Отдельный файл
`%LOCALAPPDATA%\reaper_reapy_mcp\presets\vital_catalog_<schema>.json` (override-переменная по
образцу калибровки). Схема записи: `relpath`, `size`, `mtime_ns`, `sha256[:k]` (лениво), `name`
(из имени файла), `embedded preset_name` (может отсутствовать — 549 случаев [И]), `author`,
`preset_style`, `synth_version`, флаги (`has_sample`, `sample_b64_len`, `n_wavetables_nonempty`,
`n_modulations_with_dest`). Ключ инвалидизации — **digest каталога данных** (mtime_ns+size каждого
файла, как `profile_source_rows` делает для регистри) + `catalog_reader_revision` (версия *нашего*
парсера формата, отдельная от `provider_revision` профиля). Полный скан head+tail 2226 файлов —
**0.598 с** [И]; полный JSON-разбор ~80 файлов уложился в общий прогон 0.61 с [И]; линейная
экстраполяция на 2226 файлов ≈ 15 с [П] — приемлемо как cold build, при этом метаданные лежат в
первых/последних 4 КБ, поэтому даже полный скан не требует чтения 2 ГБ корпуса (0.598 с читает
только head+tail).

**D3 — семантика `preset_search`.** Запрос: подстрока по имени файла И `author` (+опционально
`style`, `path`-prefix, `version`); лимит + пагинация через `offset`; сортировка по имени/папке;
**устойчивый идентификатор** = (relpath относительно корня данных) + `size` + `sha256` в ответе —
путь один не «устойчив» к переименованию, но переименование — это и есть другой пресет (имя = имя
файла [К]); хэш даёт доказуемость. Категории: папка (банк) + `preset_style` (9+пустое [И]) —
и **никаких тегов**, их в формате нет [К/И].

**D4 — `preset_apply`.** Сборка документа: `decode_document(file_bytes)` (файл уже разбирается как
документ [И]) → merge верхнего уровня (метаданные файла + **сохранённый живой `tuning`**) →
`plan_state_writes`/`encode_slice` в одной state-единице → существующий dry-run/verify/rollback.
Отдельным пунктом — расширить `set_path` на верхнеуровневые *labels* (`preset_name`, `author`,
`comments`, `preset_style`, `macro1..4`) с тем же обоснованием, что P30 дал для `name`/`author`/
`version` («labels free»), и **не** позволять произвольную запись `tuning` (только сохранение
исходного значения) [П-дизайн].

**D5 — `preset_save`.** Источник = живой документ (`codec.decode` → JSON) → сериализация
одной строкой с алфавитными ключами (как nlohmann `std::map` [К]) → файл в
`<data>\User\Presets\<bank>\<name>.vital` через безопасный writer (atomic write: temp+rename).
Байтовая верность писателю Vital **не требуется** (файл должен *загружаться*), но формат ключей —
обязателен (§4). Обновление браузера — вне гарантий [К]; в description тула честно писать,
что список обновится при следующем rescan.

| M3 `chorus_delay_1` → 9.123456789 | 1 | +8 | **долетела** (плагин зажал в диапазон: read-back −5.64) |

Точная граница измерена отдельным свипом (`probe_growth_boundary.py`, 2026-10-17): вырастающий
массив значений **N=16/24/28/30/32 → Δ блока +24/+32/+40/+40/+44 долетают**, **N=36/40/48 →
+48/+56/+64 не долетают** (после каждой — reset, restore `matches_capture`), т.е. граница лежит в
**(+44, +48]**. Цепочка (§10.2) использует батчи ≤ +24 и долетает.
Практическое правило для production: **одна единица state-записи должна укладываться в малую дельту**
(исторические route-ops ему удовлетворяли — потому и долетали, [И] P20).

**10.2 Пресет ДОЛЕТАЕТ цепочкой.** ZZ_AGENT_CALIBRATION_01: 68 отличающихся контролов, упакованных
в 27 батчей (каждый ≤ +24 символа) → **27/27 батчей долетели, verify ok** (единственный ожидаемый
mismatch — `beats_per_minute`); после цепочки **776/777 контролов документа равны файлу** с точностью
1e-5. Не поддался только `beats_per_minute` (файл 2.0833, read-back 2.5020) — его ведёт **хост**
(темп REAPER приходит в плагин), тот же класс, что `tuning`: значение пресета не применяется.
Вывод: `preset_apply` реализуем как **инкрементальный применитель** (батчи по бюджету), а не как
одиночная bulk-запись.

**10.3 Пере-сериализация при каждом долетевшем запросе (и её цена).** Плагин сам пере-сериализует
весь документ при загрузке state:

- **сэмпл**: каждый долетевший запрос сдвигает payload сэмпла на **ровно 4 сэмпла** (≈90.7 мкс, первые 4 — нули) — измерено на M1/T1/v3/v4 (после каждой долетевшей записи align-shift ровно −4; компенсация «payload, сдвинутый на +4» даёт ровно 0); плюс на ~1109/44100 сэмплов (2.5 %) значение уходит на **±1 LSB**;
- **floats**: возможен сдвиг на 1 ULP float32 (наблюдён на `chorus_feedback`, восстановился сам после последующих загрузок);
- **байт-точный restore через этот канал НЕВОЗМОЖЕН**: запись исходного текста чанка возвращает чанк, но плагин пере-сериализует документ, и read-back ≠ capture (v3: только сэмпл + 1 ULP). Достигнутое: документ **равен capture по всем 777+ контролам, блокам, tuning и метаданным**; сэмпл — timing точный (shift 0), остаток ≤1 LSB на 1109 сэмплах. Инверсия payload’а (v8: подать `2Y−F`) показала, что исходные байты **недостижимы в принципе**: `Q(Y)=Y−1` на этих позициях, а подача `Y±1` идемпотентна ⇒ канал стоит на фикс-поинте в ≤1 LSB от исходника (неслышно; −84 dBFS-класс на 2.5 % сэмплов).

**10.4 Что это значит для контактов:**

- `preset_apply`: achievable — но **батчами**; sample пресета применяется только как отдельный payload-путь и только при близкой длине (b64 одного листа не дробится, +58 800 символов на «+1 секунду» сэмпла в бюджет не влезают); `beats_per_minute`/`tuning` из пресета не применяются (хост/документ); wavetable-слоты — поштучно и в рамках guard’а.
- `preset_save`: по-прежнему запись файла из документа; после каждого чанк-запроса сэмпл документа проходит через ту же пере-сериализацию — **сохранение после записи фиксирует фикс-поинт, а не исходные байты** (для «сохранить как есть» без записи в плагин — файл пишется прямо из документа, это не затронуто).
- `preset_get_info`/`preset_search`: без изменений (§0).

**10.5 Три закона, найденных приёмкой реального пресета (2026-10-17, `probe_route_name_vs_growth.py`,
`probe_p38_acceptance.py`).** Выбранный пресет (`User/Presets/Jek's Vital Presets/Cyberwave/Cyberwave/
BASS Cyberline.vital`, 42 роутинга, 113 отличающихся контролов) вскрыл поведение, которого одиночные
пробы не показывали:

1. **Пара с неизвестным ЭТОМУ билду destination молча дропается плагином.** Состояние: запись пути
   `settings.modulations.1.destination = "osc_2_spectral_morph_amount"` — хост принимает
   (setter возвращает 1, Δ блока +36), read-back `""`; тот же по форме create с валидным для билда
   именем (`osc_2_spectral_morph_phase`, Δ +44) долетает и verify ok. Это ровно то, что делает и
   собственная загрузка пресета в плагине. Приёмка показала масштаб: **18 из 42 роутингов** этого
   пресета адресуют имена, которых в живом билде 1.5.5 больше нет (`modulation_N_amount`,
   `modulation_N_power` — модуляция чужой модуляции, `reverb_decay_time`, `reverb_high_shelf_gain`,
   `osc_2_spectral_morph_amount`). Последствие для контракта: такой дроп — **не** ошибка применения,
   а именованный gap (`route_dropped_by_plugin`) + `partial: true`, и транзакция продолжается;
   запоминается на билд (см. §10.6).
2. **Один путь, чей собственный рост превышает полосу, не долетает НИКОГДА и молча.** Измерено на
   том же пресете: 7 массивов `settings.lfos.N.points`/`.powers` (рост +140…+372: в файле у LFO
   больше точек, чем в живом документе) и метка `comments` (+725) читаются обратно **без изменений**,
   хотя запись «принята». Никакая упаковка это не лечит: лист не дробится. Следствие: такой элемент
   не несётся вообще (весь целиком: `num_points` без массива оставил бы живую кривую в состоянии,
   которого в пресете не было) и называется gap’ом `growth_over_budget`; в кодек добавлен предел
   `SINGLE_PATH_GROWTH_LIMIT = 36` (наибольшее значение, доказуемо внутри полосы: полоса достигает
   реальных +36, а упаковочный оценщик завышает реальную дельту на 0..12).
3. **Цена цепочки.** Применение 180-пунктового плана заняло **907 с** на этом пресете: каждый
   state-юнит заставляет перечитывать полный вектор параметров (2858 на инстанс) — это платеж за
   закон «запись документа сбрасывает обычные параметры», и он доминирует над временем записи.

**10.6 Мемо дропнутых destination.** Измеренный дроп записывается в
`%LOCALAPPDATA%\reaper_reapy_mcp\presets\vital_destination_drops.json` (рядом с кэшем каталога,
машинно-локально, ключ — `synth_version` живого документа) и учитывается при СЛЕДУЮЩЕМ применении:
такие роутинги не пишутся вовсе, а называются в `gaps` (`destination_dropped_by_plugin`,
счётчик `routes_skipped_known_drop`). Это не «затирание ошибки»: запись, которую плагин всё равно
выбрасывает, не повторяется, а сам факт остаётся видимым в ответе инструмента.

**10.7 Цена одного юнита, и три правки по её итогам (2026-10-17, вечер).** Тайминг-проба
(`probe_p38_unit_cost.py`, evidence `…191320Z…24288`) измерила каждое чтение, которое платит один
state-юнит на живом инстансе:

| примитив | медиана | примечание |
|---|---|---|
| `param_idents` (2858) | **3.03 с** | один вызов хоста на параметр (~1.06 мс) |
| `read_params` (2858) | 0.46 с | собственно значения |
| `fx_facts` | 0.28 с | внутри читает весь чанк трека |
| `read_state_chunk` | 0.063 с | |
| `locate_state_slice` | 0.094 с | |

Вектор читался **дважды на юнит** (до записи и после — измеренный закон «запись документа сбрасывает
параметры»), поэтому ~6 с из ~7.9 с на юнит приходилось на ident-таблицу, неизменную для загруженного
инстанса. Отсюда и 656 с приёмки (§10.5). Правки: (1) ident-таблица читается **один раз на
транзакцию** (свойство инстанса; таргет ревалидируется перед каждым юнитом, и смена числа параметров
сбрасывает кэш); (2) убрано ДУБЛИРУЮЩЕЕ чтение базового состояния (`_revalidate` уже его прочитал, а
запись защищена CAS) — значений читается столько же, экономится таблица; (3) бюджет батча
откалиброван по измеренному переводу оценки в реальную дельту блока: **реальная ≈ 1.4 × оценка**
(контрол с оценкой 14..16 ложится реальным +20..24), поэтому старый бюджет 12 гнал **каждый контрол
отдельным юнитом** (21 батч на 43 пути), а бюджет 24 даёт 12 батчей при реальной дельте ≤ +25 (полоса
+44/+48); 36 и 48 дают реальные +45 и +65 — за полосой.

**Найденный дефект (и исправленный): успешно записанный sample помечался провалом.** Строка отказа
показала: payload вернулся с измеренной задержкой 4 сэмпла И с реквантом — **1060 из 44096 сэмплов на
±1 LSB (2.4%)**. Три прежних применения ложились с остатком **ноль**, поэтому прежний порог (0.5%)
их пропускал, а это — отклонил. ±1 LSB — собственная truncating-реквантизация плагина int16→float32→int16
(та же полоса 2.5%, измеренная в этапе B), поэтому вердикт теперь: лёг с измеренной задержкой, каждое
расхождение — один шаг и внутри измеренной полосы; строка называет числа. Границы закреплены тестами
(`test_p38_sample_requant.py`): сдвиг больше задержки, шаг больше одного, выход за полосу — по-прежнему
провал.

**Что это дало (живьём, тот же инстанс, тот же shipping-путь):** `House Bass` — `ok, committed, 19.0 с`
(11 контролов + sample + 2 таблицы, 3 юнита); цепочка Cyberline — **38 юнитов** вместо 85–115, по ~2.8 с
на юнит (≈107 с вместо 656 с, ~6×). Остаток цены — не чтение, а ЗАПИСЬ: каждый route-create идёт
отдельным юнитом по объявленному структурному пределу (`one_route_per_state_write`), и у 18 дропнутых
+ 24 записываемых роутингов это 42 юнита, которые не сливаются.

**Лог прогона** (`plugins/logs.py`, `%LOCALAPPDATA%\reaper_reapy_mcp\logs\mcp-YYYY-MM-DD.log`): строка
JSON на вызов инструмента (длительность, ФОРМА аргументов, не содержимое) и на юнит (`index`, `of`,
`kind`, `paths`, `seconds`), плюс `unit.failed` при отказе. Очистка — при старте сервера и не чаще раза
в час (по умолчанию 24 ч, `REAPER_MCP_LOG_RETENTION_HOURS`), и трогает только свои `mcp-*.log`.
**Отменённый в редакторе вызов инструмента не отменяет запись на сервере** (измерено: отменённый
`apply` продолжил работу и применил пресет) — чтения отменять безопасно, запись нет.
